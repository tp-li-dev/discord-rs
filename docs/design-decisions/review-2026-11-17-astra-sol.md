## T1 P1 の設計（`p1-stalled-diagnostics-design.md`）

**一致した指摘：**
1. **「ディスク上のファイルへの書き込みで、I/O を最低限にできる」という主張は、根拠がない。** `fsync` なし、固定長の上書きでも、ページキャッシュの書き出し（writeback）の頻度・メタデータ（`mtime`、ジャーナル）の書き出しは保証できない。（出典：Linux の `vm` の sysctl の文書）
2. **私の実測が、これを裏付けた**（2026-11-17、WSL、デバッグビルド、アイドルの Core、300 秒）：状態ファイルあり＝書き込み 84 回・`write_bytes` 98,304 バイト（96 KiB）。状態ファイルなし（制御実験）＝すべて 0。**記録以外の書き込みは Core にはなく、増加はすべて状態ファイルの機能が原因。** 設計書の予算に対して、**予算を超えた**：(a)「30 秒に最大 1 ページ」の基準では、300 秒で最大 10 ページのところ、実測は 24 ページ（約 2.4 倍）。(b)「1 時間で 1 MiB 未満」の基準では、98,304 バイト ÷ 300 秒 × 3,600 秒 ＝ 約 1.125 MiB/時間で、予算を約 12% 超える。（(a) と (b) は別の予算の基準。測定は**デバッグビルド**、WSL（ext4）、1 回のみ。リリースビルドや別のファイルシステムでは未測定。）
3. **64 バイトの `pwrite` は、並行する読み取りに対して、原子的な 1 つのスナップショットになる保証はない。** CRC は確率的に破損を検出するだけで、原子性も鮮度も証明しない（「すべての破損を検出」は誤り）。
4. **壁時計（UNIX 時間、`mtime`）をやめ、単調時計（`CLOCK_BOOTTIME` など）と、Core の起動ごとの識別子（世代）、書き込みの連番を使う。** PID だけでは世代を識別できない。
5. 30 秒は、**「停滞の疑い」の目安であり、確定ではない**。pending の経過時間と、heartbeat の経過時間は、分けて報告する。
6. **推奨される代替：** (Sol) 検証済みの `tmpfs`（`/run`）上のファイル。ディスクへの書き出しがなくなる（ただし tmpfs はスワップを使い得る）。(Astra) ノンブロッキングのパイプ（Core → botd。固定長のフレーム、バッファの上限、`EAGAIN` で捨てる）。共有メモリ（mmap）は、同期の仕組みが要り、割に合わない。eventfd はカウンタのみ。
7. NFS は不可（ハードマウントは無期限に待ち得る）。overlayfs は避ける（コピーアップ）。DrvFs（WSL の `/mnt/...`）の挙動は未確認で、対象外。

**採用する方針（Claude の判断。ユーザーの確認待ち）：** P1 を **`tmpfs`（`/run/discord-rs/` 配下）上のファイル**に変更する。起動時に `statfs` で本当に tmpfs か確認し、そうでなければ機能を**無効にする**（ディスクには書かない）。記録に、単調時計の時刻、Core の世代の識別子、連番を入れ、botd は自分が起動した Core の PID と一致するかも確認する。設計書の誤った記述（ページの上限、CRC の保証）を訂正する。パイプ方式は、実装が大きいので、tmpfs 方式で I/O が許容できるかを実測してから判断する。

## T2 結果不明の操作と nonce（`08-unknown-outcome-operations.md`）

**公式ドキュメントと SDK ソースで確認した事実。** [Discord Create Message](https://docs.discord.com/developers/resources/message#create-message)。
- `nonce` は整数または文字列で、**25 文字まで**。`enforce_nonce=true` で、**同じ作者・同じ nonce**を、**過去数分**で一意性を確認する。重複したら、既存のメッセージを返し、新しく作らない。**期間の正確な値は、公式に書かれていない。**
- **twilight-http 0.18.0**：`CreateMessage::nonce(u64)` はある。**`enforce_nonce` の指定はない。** `payload_json` は、`attachments` 以外の他のフィールドを置き換える。
- **discord.py v2.6.4**：HTTP 送信は初回を含めて最大 5 試行。再試行の条件を満たす 429 は `retry_after` を待つ。500・502・504・524 および一部の接続リセット（`errno` 54 または 10054）はバックオフして再試行する。通常の `Messageable.send` は、指定がなければ呼び出しごとに nonce を 1 回生成し、`enforce_nonce=true` とともに送る。同じ呼び出しの HTTP 再試行では nonce を再利用する。[Messageable.send](https://github.com/Rapptz/discord.py/blob/v2.6.4/discord/abc.py#L1554-L1575)、[handle_message_parameters](https://github.com/Rapptz/discord.py/blob/v2.6.4/discord/http.py#L194-L196)、[HTTPClient.request](https://github.com/Rapptz/discord.py/blob/v2.6.4/discord/http.py#L589-L723)。
- webhook の実行、interaction の応答・追加応答には、**nonce の保証が文書化されていない**。初期応答は 3 秒の期限、トークンは 15 分。編集・リアクションにも nonce の保護はない（編集の再試行は、新しい編集を上書きし得る。リアクションの再実行は、後の削除を取り消し得る）。

**一致した指摘（設計）：**
1. 「安全な再試行」という言い方は不適切。**期間限定の重複抑止**にすぎず、永続的な冪等性ではない。
2. **論理的な送信 1 つにつき、nonce を 1 つ、最初の試行の前に割り当て**、再試行でも、作者・チャンネル・本文・nonce を変えない。**作者の全チャンネル・Gateway の世代・再起動をまたいで一意**にする。入ってきたメッセージの ID の使い回しは不可（1 つの処理が複数の返信を出す場合）。
3. **`payload_json` を使うなら、`allowed_mentions` を含む本文全体の JSON を自分で作る**（さもないと、現在のメンション抑止が、静かに消える）。
4. レート制限は、バケットと主要なリソースで扱う。**twilight は 429 を内部で再試行する**ので、競合する再試行のループを作らない。（Astra：twilight のグローバル制限の解析が `None` を返し、サーバーの待ち時間が反映されない疑い。要確認）
5. 再試行の予算を使い切ったら、**UnknownOutcome として残す**。長い待ちは、重複抑止の期間を超え得る。
6. 範囲：**メッセージ作成だけ**。webhook・interaction・編集・リアクションは、別の方針（順序のある照合）にする。

**未確認：** 重複排除の正確な期間、チャンネルをまたぐ範囲、削除・編集の後の挙動、実際の Discord での動作（実機の 2 回投稿の試験は未実施）。

## T3 Identify と Resume（`05-identify-and-resume.md`）

**公式で確認された事実（出典：`docs.discord.com/developers/events/gateway` ほか）：**
- `session_start_limit`：`total`（許される開始の数）、`remaining`、`reset_after`（ミリ秒）、`max_concurrency`。**実際の値を読む**（例の 1000/999/14400000/1 を固定で持たない）。
- Identify は、**バケット（`shard_id % max_concurrency`）ごとに 5 秒に 1 回**。通常の上限は、**全シャード合計で 24 時間に 1000 回**（Resume を除く。大きな Bot は増える）。上限に達すると、セッションが切られ、token がリセットされる。
- `1006` は Close フレームを受信せずに接続が終わったことを表す WebSocket の予約値で、Close フレームには載らない。Discord の `4000` は原因不明の切断で再接続可、`4007`・`4009` では新規セッションが必要、`4004` では再接続不可。Gateway の op 7 Reconnect は再接続と Resume を求めるイベントで、Close フレームとは別に届く。`1006` や `4000` だけでは op 7 の受信や Resume の成否は分からない。[RFC 6455 §7.1.5・§7.4.1](https://www.rfc-editor.org/rfc/rfc6455.html#section-7.1.5)、[Discord Gateway Close Event Codes](https://docs.discord.com/developers/topics/opcodes-and-status-codes#gateway-close-event-codes)、[Discord Gateway Resuming](https://docs.discord.com/developers/events/gateway#resuming)。
- Resume は、`session_id`、`resume_gateway_url`、最後に受け取った Dispatch の連番が必要。**欠けたイベントは順に再送され、`RESUMED` で終わる。ただし、受け取った後でローカルで落としたイベントは回復しない。** op 9 の `d=true` は再度の Resume が可能、`false` は新しいセッションが必要。

**Oracle の 2026-11-17 の記録：** op 7 → 4000 に続く Resume 成功が 11 件、1006 に続く Resume 成功が 1 件、直前の切断行がない Resume 成功が 1 件。前二者の時刻差は、秒に切り捨てたログの表示上で 0〜1 秒だった。実測の復帰時間がすべて 1 秒未満かは未確認。新しい `READY` は記録されていない。失敗した Identify の試行回数は未確認。これらは接続復帰の観測で、`gateway-update` の所要時間は別計測（`progress.md` の単一 Shard で約 1.1 秒、2 Shard で約 31 秒の記録など）。

**Astra が指摘した、具体的な穴：** `main.rs`（プロセス内のキュー）と `daemon.rs`（プロセスの起動の予算）は、**実際の Identify の送信を、Gateway プロセスをまたいで調整していない**。2 つのシャードが、無効なセッションの後に、独立して再 Identify し得る。**実際の Identify の送信を、botd 側の Bot ごとの 1 つのスケジューラーで調整**すべき（起動・手動・復旧の経路を含む）。また、`Ready` を数えることは、新しいセッションの成功を示すだけで、失敗した Identify の試行がゼロであることは示さない（Identify の送信、Resume の試行と結果、セッションの喪失を、token・セッション ID なしで計測する）。

## T4 了承済みの提案と、差し替え（`proposals-2026-11-17.md`、DDR-0006）

**一致した指摘（強い）：政策は妥当だが、切り替えの手順が不完全で、現在の順序は危険。**
1. **提案 1 の順序が逆。** 「新 Core へ配送を切り替えてから、重複排除の記憶を渡す」と、渡す前に重複が起きる。また、旧 Core が、スナップショットの後に受け付けた ID を、新 Core が知らず、**二重に実行**し得る。
2. **推奨される順序：準備 → 受け付けの壁（admission barrier）→ 最終スナップショット → 復元の確認（ACK）→ 配送の切り替え（commit）→ 退役。** 壁の間の新しい到着は、上限つきでバッファする。送信待ちの配送は、送る前に世代を再確認する。
3. **重複排除の記憶は、集合だけでなく、追い出しの順序つきの窓として渡す。** `SeenIds` は、**実行の前に** ID を記録する（`worker.rs`）ので、「完了した処理の台帳」ではない。4,096 件は、トラフィック次第で数秒〜数分。「まれで短い重複」とは言い切れない。
4. **重複排除の記憶の引き継ぎが失敗したら、既定は「切り替え前に中止」**（明示すれば、劣化した続行を許す）。**これは、ユーザーが了承した「失敗しても更新は止めない」（DDR-0006 の 1）の変更になる。** 劣化している状態は、カウンタと状態として、はっきり見えるようにする。
5. **世代に固定した `ApiResult`（HTTP の結果の受領）は、受領されるまで、旧 Core の接続を保つ。** 受け付けの停止が、受領の経路を止めてはいけない。接続の締め出し（fence）は、要求と要求の間に効くので、退役の間も、受領を許す設計にする。
6. **シャードごとに、Gateway の更新、Core の更新、復旧、P3 の管理操作を直列化する。** Gateway の所有 epoch と、Core の世代は別にする。切り替えの状態を記録して、クラッシュ後に復旧できるようにする。**Core の数の変更は拒否**（配送のハッシュが変わる）。
7. **P3（認証・監査つきの手動復旧）を、差し替えより先に。** 自動の停止がない以上、止まった旧 Core が溜まる。**退役中の世代の数に上限**を設け、溜まったら、更新を拒否する。
8. 他システムから**取り入れる**もの：NGINX の「新しい受け付けを止め、既存の処理を終わらせる」、Erlang/OTP の「明示的な一時停止と状態の変換」。**避ける**もの：Kubernetes の既定の「猶予の後の強制終了」（警告のみの方針と衝突）。systemd のソケット活性化は、ソケットを渡すだけで、状態や受領は渡さない。
9. **`architecture.md` §6 は、切り替え後のロールバックを許しているが、DDR-0006 は、切り戻さない方針。** どちらに合わせるか、整理が必要（Sol）。

## Top 5（2 人の一致、優先度順）
1. 切り替えの受け付けの壁・最終の重複排除の引き継ぎ・復元の確認・世代の配送・旧世代の受領のドレインを、**実装の前に仕様にする**（P0/P1）。
2. **Identify の実際の送信を、Bot ごとに 1 つのスケジューラーで調整**（Astra）。
3. 操作に固定の nonce で、有限の期間の再試行（本文全体の JSON、429 のバックオフ、UnknownOutcome の保持）。
4. **テレメトリを、ファイル I/O の保証に頼らず**、tmpfs またはノンブロッキングのパイプ、単調時計、世代つきの鮮度に。
5. P3 を差し替えより先に。退役の世代の上限。劣化した重複排除を、運用上の状態として見えるように。
