## 1. nonce の再試行
- **見立て：** 既定オフのまま、Bot ごとの設定にして試験用 Bot から有効にする。
- **Sol の指摘（コードで確認が要る）：**
  - 受信済みの HTTP エラーの**本文の読み取りに失敗**すると、twilight-http 0.18 はそれを `RequestError` として返す。現在の判定は `RequestError` を通信失敗として再試行するため、設計の「HTTP エラーは再試行しない」と食い違う（ソースからの推測。再現はしていない）。
  - 15 秒の期限は**クライアント側**の制約。Discord に渡った後の要求は、クライアントが諦めても処理され得る。別の呼び出しが新しい nonce を作れば、同じ返信が 2 件になり得る（現在は 1 回の呼び出しの中でだけ nonce を再利用）。
  - 長い 429 待ちの後の遅い再送は、この経路では防がれている（期限が制限待ちを含む、429 は再試行しない）。Twilight の制限機構に依存する。
  - 添付、コンポーネント、`message_reference`、スレッド作成、Interaction の応答と編集は、別の契約。現在の直列化は本文・nonce・メンションだけ。
- **有効化の条件：** Ubuntu で「最初の POST が成立し、応答が失われ、再送が同じ ID を返し、見える投稿が 1 件」という故障注入の証拠。重複が 1 件でも出たら、オフに戻す。

## 2. Identify の送信時の調整
- **見立て：** 単一ホストでは、起動の調整で足りる。送信時の許可は、複数 Shard を実際に使うまで後回し。
- **Sol の反論（採用）：**
  - `OP 9`（再開不可）を受けると、Twilight は**同じプロセスの中で**再 Identify を行う。botd は起動を 1 回としか記録しない。
  - Shard 1 つの更新でも、旧・新の 2 つの Gateway が存在し、どちらも再接続できる。同じ 5 秒の枠で両方が送り得る。起動間隔の延長や起動履歴の永続化では、この送信は見えない。
  - Twilight のキューは、同じキューを共有する Shard の間では 5 秒間隔を守る（`twilight-gateway-queue` 0.18 のソースで確認）。ただし、discord-rs は Gateway ごとに別のキューを作る。
  - Discord は標準で 24 時間に 1,000 回（Resume は対象外）。超えるとセッションが終了し、トークンがリセットされ得る。
- **提案された最初の形：** botd と Gateway の間の専用の継承チャネルで、Bot・Shard・世代に結びつけた短命で 1 回限りの許可を、**送信の前に永続的に記録**してから渡す。期限の確認は送信の境界で。許可を失ったら保守的に数える。調整役が使えないときは、新しい Identify は保留し、Heartbeat と Resume は通す。履歴は永続化し、再起動と時計の扱いを明示する。
- **受け入れの証拠：** モックの Discord で、受信した opcode 2 のフレーム数を数える（`OP 9 false`、Hello の遅れ、旧・新の重なり、枠の枯渇、botd の再起動）。Resume が許可を消費しないことも確認する。

## 3. Core が起こす補助プロセス
- **見立て：** 将来、基盤が `PR_SET_PDEATHSIG` ＋同一プロセスグループの起動 API を提供する。PID の登録 API は作らない。
- **Sol の反論（採用）：** `PR_SET_PDEATHSIG` は、子を起こした**OS スレッド**の終了で発火する。Tokio のブロッキングスレッドや、P3 の再起動用のスレッド（起こして終了する）に使うと、正常な子が殺される。親が先に死ぬ競合もある。プロセスグループは現在のメンバーにしか届かず、`setsid()` で抜けられる。サブリーパーは孤児を拾うだけで、終了させない。
- **最初の一手の提案：** Core の世代ごとに、委譲された cgroup v2 のサブツリーを作る。fork の前に Core を入れ、穏やかな終了を試み、必要なら `cgroup.kill`、`populated 0` と回収を待つ。Oracle での委譲・カーネルの対応は**未検証**。
- 補助プロセスの管理は、P3 の完成の主張に含めない。systemd の一括の後始末（`KillMode=mixed`）を先に確認する。

## 4. 作業の順序と「完成」の定義
- 「完成」と外部に言うなら、**単一ホストの運用の基準線**と呼ぶ。`architecture.md` §16.2 は Core の無停止差し替えと分散フェイルオーバーも求めている。
- D2 に足す基準（提案）：最終候補のビルドで 77 時間の放置と再起動後の自動起動をやり直す。本当に停滞したハンドラでの P3（世代の入れ替え、隣の Core と Gateway の継続、処理中の結果不明の扱い）。systemd 下の botd の `SIGKILL`。Identify の枯渇と再起動からの復旧。Gateway 更新の失敗とロールバック。Interaction は、見える返信の数、初回の応答の試行回数、ハンドラの実行と副作用、取りこぼしを別々に数える。複数 Bot・Shard を含めるなら、その構成の証拠と試験した上限を明記する。
- 既知の穴：負荷試験は、静止した旧 Core のクラッシュと、忙しい受領の失敗を区別しており、ハンドラ完了後の結果不明の試験は無視（ignore）のまま。リリースの証拠と運用ガイドに、この範囲を記録する。
