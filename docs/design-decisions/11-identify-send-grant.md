# 11. Identify の送信許可（DDR-0007 優先度 4 後半）

## 適用範囲

一つの Linux botd が管理する Bot の、全ローカル Shard と Gateway 世代を対象にする。botd の `--identify-send-grants` で有効化する。無効時は DDR-0007 前半の起動調整と従来の Twilight キューを使う。分散構成への拡張には既存の認証・quorum・lease と連動した共有予算が必要。同じ Discord Bot を別の Bot ID、別の runtime root、別ホスト、または外部クライアントから起動した場合は、この予算の範囲外になる。

## チャネルと互換性

- 既存の管理 stdin は botd → Gateway の停止と昇格に使う。Identify 用に匿名の Unix stream socketpair を Gateway の起動ごとに作る。二組のパイプに比べて両端で一つずつ FD を扱えばよく、パス付き Unix ソケットに必要な接続認証、名前の回収、パス長制限も不要。Core の起動引数、環境、IPC にこの経路を追加しない。
- botd は自分が起動した相手にだけ FD を継承させ、チャネルを設定上の Bot ID、Shard ID、botd のインスタンス ID と Gateway の起動番号に結び付ける。Gateway は取得直後に FD に close-on-exec を戻す。要求側が Bot や世代を指定するフィールドは持たない。
- Protocol v1 は一要求につきバージョンの 1 バイト、固定長の応答はバージョン、結果、64 bit の little-endian 値。値は許可なら同じホストの CLOCK_BOOTTIME における期限（ns）、待機なら再試行までの期間（ns）。同時に未完了の要求はチャネルごとに一件。バージョン不一致や I/O 障害でチャネルを閉じる。ログ、応答、ジャーナルには Bot token、Discord セッション ID、WebSocket ペイロードを入れない。
- 有効時の botd は v1 専用の起動引数を必ず渡す。現行の旧 Gateway は未知の引数を拒否するため、ログイン前に失敗する。未知の引数を無視する互換ラッパーは有効モードの対応外。旧 botd が新 Gateway を起動する場合は起動引数がなく、明示的に従来動作となる。有効化には対応版の botd と Gateway、および旧方式で起動した Gateway の停止・入れ替えが必要。

## 会計と送信境界

- 起動試行は既存の履歴に一枠記録する。有効時はその記録を永続化してから起動し、起動時の枠を一回限りの引換権として、その起動だけに渡す。手動 restart の停止前予約は DDR-0007 前半と同じく、停止中は他の要求から保護し、起動境界で一枠を記録する。spawn の失敗で消費は戻さない。
- Hello 後の初回要求では、同じチャネルに割り当てた起動枠だけを一時的に除外して残りの履歴で判定する。許可時に起動枠を送信許可へ置換する。間隔や窓は最後に送信できた時刻を上界とするため許可の期限から数える。起動枠が既に計数窓の外なら通常の新規枠を使う。拒否で引換権を失わず、永続化した許可は未送信・応答損失・失効でも消費済みとする。以後の Identify は毎回新規枠を要する。
- 本番のローカル値は Bot 全体で 30 秒以上かつ直近 1 時間に最大 10 枠。同一 Bot ID の全 Shard を一律に直列化するため、範囲内で Discord のキーごとの 5 秒と標準の 24 時間 1,000 回より保守的。Gateway ごとの既存 Twilight キューも維持し、起動時に取得した Discord の残量を先に適用する。外部消費や Discord の残量の継続的な再取得・照合は別途設計する。[Discord Gateway の仕様](https://docs.discord.com/developers/events/gateway#identifying)
- Cargo.lock の Twilight 0.18.0 では `twilight-gateway-queue-0.18.0/src/lib.rs:25–32` の `Queue::enqueue` は単位値だけを伝える。 `twilight-gateway-0.18.0/src/shard.rs:802–830` で Hello を処理し、セッションがある場合は Resume を直接準備し、なければキューに入れる。 `shard.rs:832–843` は Invalid Session と Reconnect を区別する。 `shard.rs:620–635,676–711` では許可受信と WebSocket の `start_send` の間に書き込み可能待ちがある。カスタム Queue で許可を非同期に待ち、固定版の最小パッチで `start_send` 直前に許可を一回だけ消費する。期限切れの Identify は捨てて再要求する。この境界より後の OS やネットワーク内の配信遅延は制御できない。
- 許可期限は発行から 2 秒。各 IPC 往復の期限は 2 秒。予算待ちは指定時間を上限 30 秒ごとに刻んで再試行する。切断・互換性エラー・IPC タイムアウトでは固定行 `Identify send grant unavailable` を出してそのチャネルの新規 Identify を保留する。既存の Heartbeat と Resume は許可の対象外。botd 再起動で旧チャネルは復元しない。旧 Gateway の生存確認と重複起動防止は既存の予約に従い、後継 Gateway は新チャネルを用いる。

## 永続化と時計

- runtime root の `identify-send-grants.jsonl` に v1 の起動と送信許可を追記する。Bot ID、Shard ID と起動世代は事業上の識別子で、要求本文や環境は記録しない。所有者、通常ファイル、単一リンク、0600、シンボリックリンク拒否を既存監査ファイルと同じヘルパーで確認し、排他ロックを保持する。親ディレクトリとファイルの同期を行い、許可レコードの同期完了前には応答しない。
- Linux の boot ID と CLOCK_BOOTTIME を保存する。同じ boot で再起動した botd は履歴を再生する。壁時計の補正は会計に使わない。boot ID が変わった場合は新 boot の観測から少なくとも 1 時間と許可の有効期間分を保留し、この待機開始も記録する。時計逆行、完全行の破損、同期失敗、ジャーナル上限の到達は新たな許可を止める。末尾の改行がない断片は同期済みの許可応答に対応しないため、排他ロック下で切り詰めて同期する。上限は 16 MiB とし、運用中の削除や自動ローテーションを行わない。

## 更新中の優先順位案

- 同じ poll で待っている現行世代を待機世代より先に扱う。既存の手動 restart 予約は守る。更新が復旧用の枠を保護している期間は、その一枠を空けたまま送信を判定する。更新失敗後に候補を止めた後の復旧は既存の起動経路を使う。
- 許可済みの枠は取り上げない。Bot 間の予算は独立。同順位の厳密な公平性、更新の長期飢餓回避、別ホスト間の優先順位は運用判断を待つ。

`botctl status` / `inspect` の各プロセス行の `identify_send_grant` は、プロトコル版、ジャーナル状態（`ready` / `unavailable`）と現行・待機チャネルの最終結果（`awaiting_request` / `granted` / `waiting` / `exhausted`）を示す。チャネルがない場合は `null`。 `granted` は永続化済みの許可を表し、Discord の受信は表さない。ジャーナルの同期は botd の監視側で行い、Gateway の WebSocket を駆動するタスクでは行わない。

## 障害と試験

| 条件 | 期待する結果 |
| --- | --- |
| Hello が遅れる | 起動だけを先に記録。実際の Identify は Hello 後の送信許可と期限検査を通る |
| Invalid Session の `d:false`、再開できない切断 | 同じ世代の再 Identify も新しい枠を使用 |
| Resume、Heartbeat | Identify の IPC と会計を通らない |
| 現行・待機の並存、枯渇 | 共通予算で許否を決め、拒否した側は Identify を送らない |
| 許可応答の紛失、待機中の切断、期限切れ | 記録済みは消費済み。期限外の送信は抑止 |
| botd 死亡、同一 boot で再起動 | 旧チャネルは終了。新チャネルも過去の枠を引き継ぐ |
| 電源断、壁時計変更、boot 変更、破損 | 同期済みの履歴を復元し、不確かな時刻では保守的に停止または待機 |

注入した時刻で、引換、間隔、回数枠、再起動、切れた末尾と時計を確認する。既存のモックは Gateway プロセスに JSON のテスト制御を送るもので Discord WebSocket を実装しない。opcode の検証には loopback 上の WebSocket で Twilight を実際に駆動し、受け取った 2 と 6 を数える。許可件数だけから送信件数を推定しない。

## ユーザー判断が必要な点

1. 有効化と旧版入れ替えの手順、2 秒の期限、botd 喪失後に旧 Gateway の入れ替えで復旧する方針。
2. 本番での保護枠数と優先順位、Discord の残量の更新頻度、ジャーナルの保守方法。
3. 複数 botd をまたぐ共有予算と、認証・quorum・lease と連動させる時期。
