# 12. ローカル管理チャネルの相互認証と接続制限

## 脅威と対象

[architecture.md](../architecture.md) §4.3 のローカル管理経路を対象とする。既存の botctl は loopback TCP の接続直後に再利用可能な secret を JSON に入れて送る。systemd の固定ポート 47321 は botd 停止中に別 UID のローカルプロセスも取得できる。取得した secret は、既定のファイル認証では shard scope のない admin に相当する。旧 manage の管理 CLI も同じ種類の送信を行う。また botd と manage は認証前に最大約 4 KiB の要求を読み、最大 32 接続が 3 秒の期限まで滞留する。

別 UID のローカルプロセスによるポートの先取り、不完全な接続、証明の再送・反射、要求・応答の改変を想定する。root、サービス UID、秘密の保管先や正規の実行ファイルを管理できる主体は信頼する。HMAC は通信内容を暗号化しない。TCP のポート占有そのもの、カーネルの接続キュー・ホスト資源の飽和、正規サーバーへの通信の透過中継は防げない。遠隔管理、quorum/lease、Gateway/Core 間の別プロトコルは今回の範囲外とする。

## 採用する設計

- botd/botctl と manage の管理チャネルは、既存 rustls の HMAC-SHA256 プロバイダーで相互認証する。サーバーが先に証明し、クライアントは検証後に自分の証明と要求を送る。生の secret は権限検査済みファイルまたは信頼済みの匿名 stdin に限る。運用で投入する secret は暗号学的乱数で生成する。
- TCP は loopback 限定とする。botd/botctl は Linux で明示指定した Unix ソケットも使用できる。TCP と排他的に選び、ソケット直上の 0700 ディレクトリと 0600 ソケットは実効 UID 所有を要求する。パスの途中もシンボリックリンクを許可せず、別 UID による置換を許す祖先を拒否する。root 所有の sticky ディレクトリは、下位要素の所有者も検査する場合に許可する。双方が SO_PEERCRED を確認し、同一 UID を要求する。さまざまな UID に capability を配布する既存 TCP 運用を考慮し、既定は据え置く。manage は引き続き TCP を使用する。
- 接続直後の処理は最大 8 件の待機枠とし、満杯なら最古の未認証接続を破棄する。初回 hello 全体を 1 秒、サーバー証明の送信とクライアント証明受信を続く 1 秒に制限する。認証前に読むのは hello と固定長の証明だけとする。クライアント証明の検証後は独立した最大 32 件の処理枠で要求を読む。未認証の接続はこの枠を消費しない。認証済み要求が自身で枠を使い切る場合や TCP に継続的な接続洪水がある場合は空きや進行を保証できない。
- 既存の principal・role・scope の割り当てと操作の監査を維持する。manage の認証拒否監査は限られた別キューを使い、認証済み要求のキュー容量を消費しない。

ポートのランダム化だけでは接続先を認証できない。サーバーの証明なしで要求を先に送る案と、旧 JSON へのフォールバックは採用しない。TCP 互換が必要なため Unix ソケット専用への切り替えは今回行わない。ローカルでの今回の要件には、別途の証明書配布を要する TLS より既存の共有資格情報を使う方式を選ぶ。

## ワイヤープロトコル v1

1 接続につき 1 要求・1 応答。固定長フィールドはそのまま連結する。マジックは botd が ASCII `DRSBOT01`、manage が `DRSMGT01`。

| 方向 | 内容 |
| --- | --- |
| クライアント → サーバー | マジック 8 バイト、独立な乱数のクライアント nonce 32 バイト |
| サーバー → クライアント | 同じマジック、独立な乱数のサーバー nonce 32 バイト、サーバー証明 32 バイト。manage は admin、viewer の順で証明を 2 個送る |
| クライアント → サーバー | クライアント証明 32 バイト。continue フレームを待たずに認証付き要求フレームを続けて送れる |
| サーバー → クライアント | 認証付き応答フレーム。送信後に接続を閉じる |

各 MAC は `HMAC-SHA256(secret, magic || label || client_nonce || server_nonce || data)` の 32 バイトを使い、定数時間で検証する。固定ラベルは `S`（サーバー証明）、`C`（クライアント証明）、`Q`（要求）、`R`（応答）とする。証明の data は空とする。フレームは `長さ (u32 BE) || JSON || MAC`。フレームの MAC の data は長さと JSON の両方を含む。JSON 末尾の改行はフレームに含めない。botd の要求は最大 4095 バイト、manage は最大 4094 バイト、応答は最大 65535 バイト。要求・応答の JSON は MAC 検証後にデコードする。主体情報の決定は、サーバー側で検証に使った資格情報に基づく。

## 互換性と移行

- 同じリリースの botctl/botd と manage CLI/常駐 core を対で切り替える。CLI 引数、匿名 stdin の JSON、secret ファイル、manage の endpoint ファイルは再利用できる。新プロトコルに認証なしのフォールバックは設けない。
- 新 CLI は旧サーバーにマジックと乱数しか送信しない。証明を得られない場合は相手のリリースと資格情報を確認する診断を返す。旧 CLI は先に secret を送る実装なので、新サーバーはマジック不一致で接続を拒否し管理操作を実行しない。旧 CLI の送信や別プロセスによる受信を新サーバー側から防ぐことはできない。旧 CLI の起動を止め、入れ替え後に新しい資格情報を旧 CLI に渡さない運用とする。過去の漏えいが疑われる場合は切り替え時に更新する。
- Unix ソケットを選ぶ場合は 0700 の専用ディレクトリをサービス UID 所有で用意し、botd に `--secret-file ABS --control-socket ABS`、同じ UID の botctl に `--secret-file ABS --socket ABS` を指定する。既存のソケット名を自動で削除して横取りしない。異常終了後は同じパスを使用するプロセスがないことを確認し、管理者が残存パスを処理するか systemd 管理の runtime ディレクトリを再作成する。

## 障害時の扱い

| 条件 | 結果 |
| --- | --- |
| 旧版・偽サーバー・マジック不一致・証明なし／不正 | 新 CLI は要求やクライアント証明を送らずに中断。サーバーは管理操作を受理しない |
| nonce が異なる再送・方向を変えた反射・改変された要求 | 検証失敗。操作を受理しない |
| 期限までに hello／証明が揃わない、未認証枠が満杯 | 当該接続または最古の未認証接続を破棄 |
| 認証後に要求が欠落・過大・不正、または処理枠が満杯 | 接続を閉じる。監査または操作受付の可否は既存の制御側が決定する |
| 受理後に接続切断・応答 MAC 不一致 | 受理済み操作を取り消さない。操作 ID がある場合は operation で照会する |
| Unix パスの所有者・モード・種別・相手 UID が不正 | bind／接続／認証前の受理を拒否 |

## 試験と運用判断

- 実 CLI が偽サーバーへ出す初回バイトと、不正証明の後に送らないことを検査する。新旧の両組合せで操作が受理されないことを検査する。
- nonce を変えた MAC の再送、クライアント証明の反射、要求・応答の改変、長さ上限と初回期限を検査する。
- 実 botd と legacy manage へ 32 件以上の idle 接続を保持した後、認証済み status を完了させる。既存の認可・監査・操作・再照会テストも新版のワイヤーで実行する。
- Linux の Unix ソケットで同一 UID の接続と、相手 UID の不一致、所有者・モード・リンクの拒否を検査する。統合試験のソケットは /tmp 配下の短いパスを使う。
- 本番の既定を Unix ソケットにする時期、同一 UID でない運用者の移行方法、旧 CLI 停止と資格情報更新の日程は運用者が決める。本変更は既定ポートや稼働中の資格情報を変更しない。
